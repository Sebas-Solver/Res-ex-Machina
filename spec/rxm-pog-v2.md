|---|---|
| **Status** | Draft, 2026-10-02 |

The key words MUST, SHOULD and MAY are to be interpreted as in RFC 2119.

## 1. What this profile says, and what it does not

A valid rxm-pog-v2 anchor supports exactly this statement:

> The key of `agent` signed a declaration that content with SHA-256 `contentHash` was generated with the declared model, runtime and process, and that declaration existed no later than block *B* on chain *C*.

It does **not** prove that the declared model produced the content, that an AI produced it, who controls the key, or when the content was actually created. `modelId`, `runtimeId`, `processType`, `humanIntervention`, `pipelineSteps` and `declaredAt` are **declarations by the signer**. Implementations and user interfaces MUST present them as declared, never as verified.

## 2. Relation to ERC-8263

ERC-8263 defines a single anchoring event:

```solidity
event AnchorProof(uint8 agentIdScheme, bytes32 indexed agentId,
                  bytes32 indexed proofHash, address indexed operator, bytes aux);
```

The ERC deliberately leaves the meaning of `proofHash` to profiles and states that `operator` is **not** an authorization claim. This profile supplies the missing authorization: the agent's own signature over the full declaration, carried in `aux`, so that anyone can check from chain data alone who made the declaration, whoever paid for the transaction.

### 2.1 Independence from ERC-8263

ERC-8263 is a draft and may change, stall or be replaced. This profile is split so that does not matter:

- **Core (§3, §7 steps 3–5 and 8, §8):** the declaration, its EIP-712 digest and the agent's signature. Independent of any anchoring standard.
- **Binding (§4, §5, §6, §7 steps 1–2 and 6–7):** how the digest and signature are put on chain. The only binding today emits the ERC-8263 `AnchorProof` event from a contract deployed for this purpose, so it works whether or not the ERC is ever finalised.

If another anchoring standard appears, it gets its own binding (its own `verifyingContract` and event format). Anchors made under earlier bindings stay verifiable with their binding.

## 3. The declaration

### 3.1 EIP-712 domain

```json
{ "name": "ResExMachina PoG", "version": "2",
  "chainId": <chain where the anchor is emitted>,
  "verifyingContract": <address of the ERC-8263 contract> }
```

`chainId` and `verifyingContract` MUST be the real values of the anchoring deployment. A declaration signed for one chain or contract cannot be anchored validly on another. This removes the cross-network replay of v1 (`chainId 0`).

### 3.2 Type

```
PoGDeclaration(
  address agent,
  bytes32 contentHash,
  bytes32 inputHash,
  string  modelId,
  string  runtimeId,
  uint8   processType,
  uint8   humanIntervention,
  uint16  pipelineSteps,
  uint64  declaredAt,
  bytes32 nonce,
  bytes32 metadataHash)
```

| Field | Rule |
|---|---|
| `agent` | Address of the signing key. MUST equal the recovered signer. Externally owned accounts only in this version |
| `contentHash` | SHA-256 of the **exact bytes** of the generated content. Any re-encoding, crop or edit produces a different hash |
| `inputHash` | SHA-256 of the exact input or prompt bytes, or `0x00…00` if not committed |
| `modelId` | Declared model identifier, `provider:model[:version]`, 1–128 UTF-8 bytes |
| `runtimeId` | Declared runtime or tool identifier, 1–128 UTF-8 bytes |
| `processType` | `0` direct, `1` pipeline, `2` iterative, `3` autonomous. Other values are invalid |
| `humanIntervention` | `0`–`5`, same scale as v1 (`pog-v1-spec.md` §3.6) |
| `pipelineSteps` | ≥ 1 |
| `declaredAt` | Unix time in seconds, as declared by the agent |
| `nonce` | 32 random bytes chosen by the agent. MUST be unique per agent |
| `metadataHash` | SHA-256 of the RFC 8785 canonical JSON of the record's metadata (tags, external references, provenance such as a C2PA manifest hash), or `0x00…00` if there is none |

The metadata itself is stored off chain. Committing its hash means it can no longer be altered without detection, which closes the v1 gap where metadata was neither signed nor anchored.

### 3.3 `proofHash`

```
proofHash = hashTypedData(domain, PoGDeclaration)   // the EIP-712 digest
```

The anchor therefore commits to **every** declared field, the agent address and the domain.

## 4. Single anchor

| Event field | Value |
|---|---|
| `proofHash` | EIP-712 digest of the declaration |
| `aux` | `0xf0b2fcb5` ‖ `signature`, exactly 69 bytes |
| `agentIdScheme` / `agentId` | See §6 |
| `operator` | Whoever submits the transaction: the agent itself or a relayer. Carries no meaning for this profile |

`0xf0b2fcb5` = first 4 bytes of `keccak256("rxm-pog-v2/single")`.
`signature` = 65 bytes `r ‖ s ‖ v`, with `v ∈ {27, 28}` and **low-s** (`s ≤ n/2`). High-s signatures MUST be rejected.

Submission uses `anchorWithAux(agentIdScheme, agentId, proofHash, aux)`.

## 5. Batch anchor

For volume, many declarations can share one anchor.

| Event field | Value |
|---|---|
| `proofHash` | Merkle root over the EIP-712 digests of the declarations |
| `aux` | `0xbc7db884` ‖ `bundleHash`, exactly 36 bytes |
| `agentIdScheme` / `agentId` | `0x00` / `0x00…00`. Identity lives in each declaration |

`0xbc7db884` = first 4 bytes of `keccak256("rxm-pog-v2/batch")`.

Tree construction, domain-separated against second-preimage attacks:
- `leaf = keccak256(0x00 ‖ digest)`
- `node = keccak256(0x01 ‖ min(a, b) ‖ max(a, b))`, children sorted as unsigned integers
- leaves are taken in bundle order; an odd node at the end of a level is promoted unchanged.

The **bundle** is a JSON document listing, for each leaf, the declaration and its signature. `bundleHash` is its SHA-256. The bundle MUST be published at a location the anchoring party keeps available, and each receipt MUST carry its declaration, signature and Merkle proof, so it can be verified without the bundle.

Batch anchors are not indexed by agent. Use single anchors when per-agent lookup on chain matters.

## 6. Agent identity

| Scheme | `agentId` | When |
|---|---|---|
| `0x01` REGISTRY | `bytes32(uint256(erc8004AgentId))` | The agent has an ERC-8004 record |
| `0x02` URI_HASH | `keccak256("eip155:" + chainId + ":" + lowercase(agent))` (CAIP-10, lowercase hex) | Default: the agent is known only by its key |
| `0x00` ANONYMOUS | `0x00…00` | Batch anchors only |

Under scheme `0x01`, verifiers SHOULD resolve the registry's current wallet (`getAgentWallet(agentId)`) and report whether it equals `agent`. A mismatch at verification time does not invalidate the signature: keys rotate. It is reported as such.

**Neither scheme proves who controls the key.** Binding a key to an organisation, for example through a signed `/.well-known/` file on its domain, is out of scope of this version.

## 7. Verification

Inputs: the declaration, and either the signature plus anchor locator (`chainId`, `txHash`, `logIndex`) for a single anchor, or the signature, Merkle proof and locator for a batch anchor. Optionally, the content bytes.

1. Read the log at the locator from chain state (any RPC, archive node or light client). It MUST have the ERC-8263 `topic0` (`0x9fe832d8…23cc`) and MUST be emitted by `domain.verifyingContract` on `domain.chainId`.
2. Decode `agentIdScheme` and `aux`, and check the selector and length (§4 or §5).
3. Compute `digest = hashTypedData(domain, declaration)`.
4. Single: `digest` MUST equal `proofHash`. Batch: the Merkle proof from `digest` MUST reproduce `proofHash`, and `sha256(bundle)` MUST equal `bundleHash` if the bundle is checked.
5. Recover the signer from the signature over `digest` (low-s only). It MUST equal `declaration.agent`.
6. Single: check `agentId` per §6 (`0x02`: recompute; `0x01`: resolve and report).
7. Read the block timestamp. If `declaredAt` is more than 300 s after it, report "declared time is after the anchor".
8. If the content is available: `sha256(content)` MUST equal `contentHash`.

The result is the statement of §1, filled in with the chain, block number and block time. Steps 1–5 use chain state and the declaration only. **No RxM service is needed.**

## 8. Replay, duplicates and ordering

- Cross-chain and cross-contract replay is prevented by the domain (§3.1).
- The ERC-8263 contract does not enforce nonce uniqueness. Re-anchoring an identical declaration produces the same `proofHash`. Verifiers MUST treat the **earliest** anchor (lowest block, then lowest `logIndex`) as the one that sets "existed no later than", and later ones as duplicates.
- Two different declarations always differ in `proofHash`, even with the same content, because the nonce differs.
- An agent that reuses a nonce for different content creates two valid but conflicting declarations under its key. Indexers SHOULD flag `(agent, nonce)` collisions.

## 9. Test vectors

[`vectors/rxm-pog-v2.json`](vectors/rxm-pog-v2.json) contains a single anchor (declaration, digest, signature, `aux`, CAIP-10 `agentId`, example calldata) and a three-leaf batch (digests and root). It was produced by `node spec/vectors/generate.mjs`. An independent hand computation of the EIP-712 encoding reproduces the digest and the signer, and the signature is low-s.

The signing key in the vectors is **Hardhat/Anvil test account #0**, which is public. Never use it with real funds.

## 10. Migration from v1

| v1 | v2 |
|---|---|
| `schema: "pog.v1"`, string `content_hash` with `sha256:` prefix | `bytes32 contentHash`, SHA-256 implied |
| `timestamp` ISO-8601 string | `declaredAt` Unix seconds |
| `nonce` string, 16–128 chars | `nonce` bytes32 |
| `process_type` string | `processType` uint8 (same four values) |
| — | `inputHash`, `metadataHash` (new, may be zero) |
| Domain `chainId 0`, contract `0x0` | Real chain and ERC-8263 contract |
| On chain: `receipt_hash` in the calldata of a transaction to the operator's own address | ERC-8263 `AnchorProof` event with the full digest and the signature |
| Verification needs the operator's database | Verification needs chain state only |

v1 records remain verifiable as they are. They are not converted: a v1 signature cannot be re-used as a v2 signature.

## 11. Open points

- Contract wallets (EIP-1271, ERC-4337 accounts) as `agent`.
- A standard way for a provider or a TEE to co-sign a declaration ("attested" rather than "declared" fields).
- Binding keys to organisations (domain-based).
- Whether to propose this profile, or parts of it, upstream in the ERC-8263 discussion.
